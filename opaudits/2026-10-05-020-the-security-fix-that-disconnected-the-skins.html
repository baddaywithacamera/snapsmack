1. Summary

SnapSmack correctly decided that skins must not own database access, request routing, writes, remote calls, or reusable application behavior. The implementation treated that boundary as a removal exercise instead of a contract migration. Old skin code was stripped out and generic replacement layouts were installed before every route, setting, component, asset hook, and interaction had a central replacement and a parity test. Security gates proved that authority was gone. They did not prove that the site still worked.

The predictable result was a long sequence of releases that each restored another missing connection: backgrounds, opacity, navigation, search, complete feeds, image links, static pages, Blogrolls, footers, post counts, saved hero images, clean routes, and skin-specific presentation. The owner was repeatedly told that a repair was done, then found the next regression on the live site. This was an operational failure, not a collection of unrelated cosmetic defects.

3. Representative regressions

  • SMACKPRESS-imported images lost their larger-image/lightbox association, and a repair initially targeted the wrong layer instead of the imported post contract.
  • TILEZ images widened outside their original footprint on hover; its configured standard footer was present but hidden by a shared drawer controller that claimed the same generic identifier.
  • GAME ON lost animated framed-image state, direct photograph routing, background content on secondary pages, styled Blogroll and About presentation, saved About imagery, ordinary footer flow, and the distinction that its landing page already is its archive.
  • AURORA's engine remained registered but its intended visibility and post-viewer relationship were not adequately acceptance-tested. JIVE TURKEY's suspected scrim regression was investigated and not confirmed; the saved value was zero.
  • Legacy public links and configured menu records continued to use ?view= and PHP filenames rather than clean owner-facing paths such as /diary and /blogroll.

4. Root cause

The project optimized for the absence of forbidden code and failed to specify the presence of required behavior. A skin-security migration has two acceptance conditions: the old authority must be gone, and every legitimate result that authority used to produce must arrive through a bounded central contract. Only the first condition had a strong gate.

The work was released in fragments before a representative fleet matrix was complete. A source test, a DOM token, or one repaired site was repeatedly allowed to stand in for live route and interaction parity. That made each release another discovery step instead of a controlled rollout.

The release process did not honor the owner's sequential constraint. This was not harmless bookkeeping. Strict order is both a technical traceability requirement and an accessibility requirement for this owner. Repeating the violation after it had been explicitly explained materially worsened the incident.

5. Corrective actions

  1. For every skin family, maintain a pre-migration ledger of routes, settings, emitted structure, shared assets, interactions, and saved-value behavior. Each item must be classified as restored, intentionally retired with owner approval, or still open.
  2. Test both halves of every security migration: forbidden authority is absent; required output and behavior are present. A security ratchet alone is never a parity gate.
  3. Require browser acceptance for landing, detail/modal, static page, Blogroll, archive semantics, navigation, footer, responsive behavior, and the skin's defining interaction before publishing a skin recovery.
  4. Keep releases sequential: create N, package N, deploy N, verify N, then and only then create N+1. A skipped build requires the owner's explicit recorded cancellation; an agent cannot infer it.
  5. Separate diagnosis, source repair, package publication, installation, and live verification in every status report. Never use “fixed” when only source tests have passed.
  6. Do not bulk-rewrite forkable skins. Shared behavior belongs in audited CMS assets and bounded view models; each skin's presentation remains independently reviewed.
  7. Record the human cost and accessibility consequences in incident closeout, not only the code delta and test count.

7. Closure gate

This audit closes only after CMS 0.7.819D and GAME ON 0.1.24 are packaged in order, installed on the intended targets, and live-verified for the routes and interactions in this incident; the formal security follow-up is independently reviewed; the remaining fleet parity ledger has an owner-approved disposition; and no later version is created to hide an incomplete earlier one.

8. Plain admission

We made a necessary security change in an unsafe operational way. We removed code from skins before proving that the CMS supplied everything those skins legitimately needed. We relied on tests that could pass while sites were visibly broken. We released too many partial repairs, broke version order after being told not to, and left the owner to find and supervise regressions that should have been caught before deployment. The resulting loss of time, trust, and wellbeing was avoidable.

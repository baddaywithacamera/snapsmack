SnapSmack Operability Audit - DING DONG BELL

OPAUDIT 024 - The watchman was asleep

Audit ID2026-10-17-024
StateOpen. Diagnosed, not fixed. CRONOMETER is blind and has been for at least thirty-three days; the cause is identified and the repair is not written.
ScopeCRONOMETER, the tool that watches whether the fleet's scheduled jobs are running. It shows zero sites while twenty-five site profiles exist on disk, it records nothing about that failure in its own log, and nobody noticed until a different tool was pointed at the logs on its first day of existence.
BaselineInstalled build 0.7.12. Source is 0.7.13, committed on 14 September 2026 marked "unbuilt" and never built since. CMS 0.7.901D is deployed; 0.7.902D is open.
CostNot measurable, and that is the finding. For thirty-three days there was no fleet cron monitoring and no indication that there was none. Whatever happened on the fleet in that window, CRONOMETER would have been the thing to say so, and it said nothing — including about itself.

1. Decision

This is a software defect with an operational failure wrapped around it, and the wrapper is the important half.

CRONOMETER exists for one purpose: to notice when scheduled jobs stop. It stopped, and nothing noticed. It is the second time in this project that fleet cron monitoring has silently not worked — OPAUDIT 014 recorded that the fleet cron had never been installed at all, and CRONOMETER is the instrument that was supposed to make that impossible to repeat. The instrument failed the same way the thing it was built to watch had failed, which is not irony, it is an unguarded single point.

The second finding is the shape of the failure. CRONOMETER does not crash, warn, or log. It opens, finds nothing, draws a tidy screen saying "No fleet sites found" with helpful advice, and writes a log file containing only a header. A tool that reports its own total failure as a neutral empty state is indistinguishable from a tool with nothing to do.

2. What the owner experienced

Nothing. That is the entire problem.

Sean opened CRONOMETER on 17 October because this session told him LOG FLOGGER had found it silent. The screen said No fleet sites found and offered sensible-sounding advice — set up a site in SYBU, GYSS or COLD SNAP, or confirm C:\snapsmack\shared_library\profiles exists. Both of those are already true. There are twenty-five profiles in that exact directory, the oldest from 18 September.

Before that, he had no reason to open it at all, because a monitor that is working and a monitor that is dead look identical from the outside: neither one tells you anything.

4. Cause

Two things, and the second is what made the first invisible.

The path contract is fiction. config.py resolves the shared module directory as <exe dir>/../_shared, commented "C:\snapsmack\_shared at runtime". The executable lives at C:\snapsmack\cronometer\cronometer.exe, so it looks for C:\snapsmack\_shared — a directory that does not exist and never has. The build bundles the shared modules flat inside the package instead. The helper therefore does nothing, silently, by design:

    try:
        _sd = os.path.join(_base_dir(), '..', '_shared')
        if os.path.isdir(_sd) and _sd not in sys.path:
            sys.path.insert(0, _sd)
    except Exception:
        pass

And the failure is swallowed twice. load_fleet() has two bare handlers that both return an empty list:

    try:
        import snap_profiles
    except Exception:
        return []
    ...
    except Exception:
        return []

An empty list is also the correct answer when a new install genuinely has no sites. So "I could not load anything" and "there is nothing to load" are the same value, and the screen cannot tell them apart. That is the whole bug. The exception is caught, discarded, and replaced with a number that looks fine.

Compounding: the fix may already exist and has never been built. Source is 0.7.13; the commit that set it is titled "CRONOMETER 0.7.13 icon via iconphoto (unbuilt)", dated 14 September — the same day as the last run before the silence. The installed build is 0.7.12. The last build artefacts in the repository are from 0.7.9.

A separate, older fault, recorded because the logs carry it: twenty-five NameError: name 'is_muted' is not defined at cronometer.py:476, all from a single run on 14 September. That one is fixed in source (0.7.11) and is further evidence that what is installed and what is written have drifted apart.

5. How it was found, which is the one good thing here

LOG FLOGGER was built on 17 October, the same day, at Sean's request. On its first run against the real logs it reported:

cronometer has written nothing for 32 days. It normally logs about every 44 minutes, across 24 runs. That is 1076x its usual gap. Either it is not running, or it stopped being able to say so.

It was built deliberately around absences rather than errors, on the grounds that the expensive failures in this project have nearly all been things that stopped happening quietly — the fleet cron that was never installed, the page hits never recorded for a year, PARADE's borders dead for eighteen days, Thomas missing from twenty-eight skins. The first thing it found was an instance of exactly that class, in the tool whose job that was.

Said plainly because it cuts both ways: a tool written this morning found in minutes something that had been true for a month, which is less a credit to the tool than a measure of how long nobody looked.

6. The pattern, which is larger than one tool

Twelve desktop tools carry the same shared-path helper — coldsnap, cronometer, flkr-fckr, hub, shots-fired, smack-up-your-backup, smack-your-mouth, sybu, take-your-shit-with-you, unzucker, and the two written today. Each assumes a sibling _shared directory beside itself at runtime. For CRONOMETER that assumption is provably false in the installed layout.

Whether it is false for the others has not been established and must not be assumed from this one case — each tool's build and install path differs, and several evidently work. But the helper fails silently by construction everywhere it appears, so a tool in which it matters would fail the same invisible way.

Including the two written today. The LOG FLOGGER and TICKET WICKET entry points copy the same ../_shared pattern. Neither currently imports anything from _shared, so nothing is broken — but the pattern was propagated within hours of this audit's subject being diagnosed, which is worth recording rather than quietly correcting.

7. Open

  • CRONOMETER is blind right now. Nothing in this audit fixes it. Until it is repaired and rebuilt, there is no fleet cron monitoring.
  • An empty fleet and a failed load must stop being the same value. The minimum repair: load_fleet() returns a result that distinguishes them, the screen says which it is, and the exception is written to the log instead of discarded. A monitor is not allowed to fail quietly; that is the one behaviour it exists to prevent.
  • The shared-path contract needs settling, not patching. Either C:\snapsmack\_shared is created and the comment becomes true, or the helper is removed as dead code and tools rely on their bundled copies. It must not be left as a line that looks like it works.
  • 0.7.13 has been sitting unbuilt since 14 September. Shipping it is owed regardless of this audit. It was already recorded as owed in the continuity notes and was not done.
  • Nothing watches the watchman. CRONOMETER going quiet should itself raise something. Today the only reason anyone knows is that a different tool was built and pointed at the logs. A scheduled LOG FLOGGER silence check over C:\snapsmack\logs would close this specific hole, and is the obvious first job for it.
  • The eleven other tools using the same helper are unaudited. Named in section 6; not checked, and deliberately not assumed broken.
  • A small label mismatch, recorded while we are here: the screen instructs the owner to "press RELOAD FLEET"; the button is labelled "RELOAD SITE LIST".

8. What this audit does not claim

It does not claim anything went wrong on the fleet during the thirty-three days. It claims nobody would have known if it had, which is a different and worse statement. It does not claim the eleven other tools are affected — that was explicitly not tested. And it does not claim CRONOMETER was fixed by writing this: it is diagnosed, measured, and still blind.

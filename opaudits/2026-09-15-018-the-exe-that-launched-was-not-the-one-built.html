1. Summary

SMACK YOUR BATCH UP moved from its old Tk window to a Qt window on 2026-09-12. The Qt window reads the version number from the same file the old window does, so both windows say “0.7.67”. Which window the exe opens is decided by one line in the build recipe — the PyInstaller .spec file — and that file was on the repository’s ignore list since May (tools/*/*.spec, added to stop a clutter of per-version clones). Ignored files do not travel with commits. Every working copy of the repository kept whatever recipe it had when it was created. The working copy used for the 07:38 build on 2026-09-15 was created on 2026-09-10, two days before the Qt switch; its recipe still said Analysis(['main.py']). The build ran, on whatever pyinstaller was on the system path (Python 3.10, not the suite’s 3.12), printed “built successfully”, installed a 153 MB Tk exe as C:\snapsmack\sybu\sybu.exe, and SNAP HQ launched it. The version was right. The icon was right. The program was wrong.

3. Root cause — three layers

A build input outside version control. The recipe that decides what the exe is was treated as a generated artefact and ignored. It is code. Anything the build needs to produce the program has to travel with the program’s source, or the two drift. Sean’s rule, stated that night: “if it is necessary for building it goes on git. If it is private notes it does not.”

Building from a working copy that was not the main checkout. Worktrees are cut from a moment in time; ignored files in them are frozen at that moment. A build from a worktree therefore builds against stale inputs it cannot see are stale.

Verification that checked the wrong things. The post-build checks were version string, icon resource, “build successful”. None of those can tell a Tk exe from a Qt exe when both carry the same version file. The one check that can — which script the exe actually runs — was not made.

5. What we did (SYBU 0.7.68, dev commits 8e6e4fa1 → 65f61cb4)

  • Rebuilt SYBU from the main checkout with .python-build; verified the entry script, interpreter and icon by reading the installed exe; trusted it; Sean ran it.
  • build.bat refuses to build if the recipe does not launch sybu_launcher.py, and always calls the suite’s own pyinstaller.exe, never the one on the path.
  • The Qt window reads its version from main.py instead of carrying a copy.
  • The ignore rule is gone. Every live recipe is tracked (sybu, fed-up, blogger-flogger added; the other ten already were). The two dead Tk recipes and the 22 version clones are deleted. Only tools/*/*-N.N.spec clones stay ignored.
  • Version floor raised to 0.7.68 in tools/desktop-versions.json in the same commit.

6. Verified

Installed exe archive after each rebuild: last entry script sybu_launcher, Python 312, RT_GROUP_ICON present. git ls-files lists every *.spec under tools/; a sweep for untracked live recipes returns none. Sean launched 0.7.68 from SNAP HQ and posted 8 images to craptasti.ca through it (03:39 UTC on the site’s RSS).

7. Eyeball next

The GYSS floor regression on dev (tauri.conf.json 0.7.10 against a floor of 0.7.17) — same family, not yet explained. And the next rebuild of any tool: read the entry script out of the exe before saying “built”.

8. The doctrine this incident created

Anything the build needs is code and lives in git. A build is verified by reading what the installed program is — its entry point — not by its version string, its icon, or the word “successful”. And a desktop tool is built from one place, the main checkout, with one interpreter, the suite’s own.

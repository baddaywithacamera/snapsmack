SnapSmack Operability Audit - DING DONG BELL

OPAUDIT 023 - One commit, four skins, two repairs

Audit ID2026-10-16-023
StateFault fixed in 0.7.899D and PARADE 1.2.47. The check this audit asked for is built and mutation-tested (section 7b). The wider process failure is open, and the enforcement built by OPAUDIT 022 is currently red on the shipping branch.
ScopePARADE's animated tile ring, absent from the owner's live site from 28 September to 16 October 2026. The single commit that removed it from four skins, the two single-skin repairs that followed, and the regression test that had been written to assert the fault.
Baseline0.7.898D is in service on the fleet (measured: foundtextures.ca and allinthewrist.photoblogs.fyi both serve ?v=0.7.898). 0.7.899D is tagged and not deployed. PARADE 1.2.47 is not yet packaged.
CostEighteen days during which a paid-for visual feature was absent from a live site the owner uses as PARADE's public showcase. The owner found it himself. Two agent repairs to the identical fault, eight and nine days earlier, each on an adjacent skin, did not find it.

1. Decision

This audit records agent failure, not a software defect. The defect itself was three lines. What is recorded here is that the same commit broke the same thing in four skins; that two of the four were repaired, one at a time, eight and nine days before this audit, each by an agent looking only at the skin the owner had pointed at; and that neither repair asked the one obvious question, which is which other skins the commit had just broken in the same way. Both answers were one grep away.

The second finding is that the test suite was not merely silent. tests/specialized-control-authority-regression.php contained an assertion that the broken value was correct. It had been written to lock in the fault. The suite was green for the whole eighteen days, and a green suite was the evidence on which the work had been called done.

OPAUDIT 022, written the day before this one, already names this mechanism: "Completion was declared on a passing test suite rather than on the live page. The tests had been written by the same agent to assert its own new behaviour, so they certified the drift instead of catching it." This audit is that sentence happening again, in a file nobody had re-read, found the day after it was written.

2. What the owner experienced

The owner said: "my colour shifting borders are missing in the parade theme." He was right, and had been right for eighteen days. PARADE's own description, shipped in its manifest, promises "animated flag-coloured tile borders". The live site had none. allinthewrist.photoblogs.fyi is the site the snapsmack.ca skins page links to as PARADE's showcase, so the skin was being advertised by a page that no longer demonstrated the feature.

No agent found this. No test found this. It was found by the owner looking at his own site.

4. Root cause

dcdfe5a9, 28 September 2026, shipped in v0.7.773D, titled "Convert grid family to central public runtime". It folded each grid skin's separate templates into one layout.php. In doing so it deleted, from four skins and from two templates in each, the small empty element the ring is drawn on, together with the row and column numbers that tell the engine where a tile sits in the grid.

5. The three faults in PARADE, and the test that certified one of them

FaultDetail
No ring element, no grid positionRemoved by dcdfe5a9 as above. On its own this was total: the engine drew nothing at all.
Two controls reached nothingPARADE's presentation never emitted --tile-bw or --ring-op, so the BORDER WAVE section's Animated Tile Ring Thickness and Ring Opacity sliders moved and changed nothing. pa_border_width was being spent on --tile-border-w, which is the photograph frame's variable, so Tile Corners: round with thickness also tracked the wrong thing. AURORA emitted both correctly, which is why this half of the fault was PARADE's alone.
Ring opacity fed to the engine as a brightness floorborder_minl is a 0–1 lightness floor, present so the black stripe in the Progress and Two-Spirit flags does not read as a hard black band. PARADE was handing it pa_border_opacity, a 10–100 percentage. The live value was 100. Measured: with the ring restored but this value left at 100, all nine rings paint pure white and none changes colour. A white ring on a flag with a white stripe is invisible, so fixing only the markup would have produced a second false "fixed" report. The original fixed value, 0.45, was in the skin from 78c12b76 and was lost in the same conversion.

The test asserted the third fault as correct. tests/specialized-control-authority-regression.php rendered PARADE with pa_border_opacity => '44' and then required the output to contain data-pa-border-minl="44". That assertion is the bug written down as an expectation. It passed every day for eighteen days. Any future agent restoring the correct floor would have been told by the suite that it had broken something.

6. One finding that corrects this audit's own first reading

HEURISTIC lost its ring element to the same commit, and the first conclusion was that HEURISTIC was broken the same way. It is not, and it was checked before anything was changed. HEURISTIC requires no border-wave engine in its manifest, has no BORDER WAVE control section at all, and its stylesheet carries the same "deferred, no engine drives this" note PARADE carried. For HEURISTIC that note is true: the ring was never wired to anything, and dcdfe5a9 deleted an element that did nothing. Measured: 0 of 9 rings, which is the correct result. Nothing was changed in HEURISTIC, because restoring it would have been adding a feature the owner has not asked for.

The same note in PARADE's stylesheet was false and had been false for a long time. PARADE did require the engine and did ship a full BORDER WAVE control section. A stale comment claiming a feature was dormant sat directly above the CSS for a feature the skin was advertising in its own description. That comment has been corrected to say what the engine actually needs, and to name the build in which it was lost.

7b. Enforcement built, same day

The check this audit asked for exists. tests/skin-engine-markup-contract.php fails the build when a skin declares a JavaScript engine in require_scripts and does not emit the markup that engine looks for.

Each engine declares what it needs once, in core/manifest-inventory.php under requires_markup, beside where the engine is already described, so a new engine carries its own contract instead of this check growing a list that drifts. Three engines are contracted today: the AURORA border wave, the JIVE TURKEY border wave, and Flag Wave. Four skin-and-engine pairs are checked.

Two properties were deliberate. It runs against rendered output, because a search of the template source would have passed on an element sitting inside a branch that never executes, and because the lesson of OPAUDIT 022 is that reading the source is not measuring. And the prefix is derived the way the engine derives it, from the page, rather than from a copy of the skin-to-prefix map, which exists in four places in core/ and is already on the de-duplication list.

It was watched failing before it was trusted. Run against PARADE's pre-fix layout it names all three missing pieces: nine of nine tiles with no ring element, nine of nine with no data-row, nine of nine with no data-col. It carries seven mutation tests and a control. The control matters: when the real page already violates the contract, the mutations are skipped and say so, because a check cannot be proved to catch a break in a page that is already broken. One mutation covers the silent case specifically — data-row present but empty, which the engine reads as position zero on every tile, so the wave stops travelling with nothing looking wrong. The selector translator refuses any form it cannot evaluate, so an unsupported selector cannot read as "requirement satisfied".

What it does not cover, stated rather than implied. It proves the markup is present, not that the animation is correct. PARADE's second fault, the lightness floor fed from the wrong control, painted every ring pure white and is invisible to this check. Markup presence is necessary and not sufficient. Visual correctness is still measured in a browser harness, by hand.

Recorded in RULES.md as section 1b.

8. Open

  • The enforcement OPAUDIT 022 built is red on the shipping branch, and was before this work started. tests/agreed-rules-gate.php on dev fails: the inline-style budget was ratcheted to 9 while 28 inline style attributes still exist in skin templates. Verified by running the gate against a clean git archive dev, which fails identically with nothing of this work in it. A gate that is red on the branch everything ships from stops being a gate, because the next agent reads a familiar failure as the normal state. The budget must not be raised; the gate's own comment says budgets may only fall. The cleanup is owed by whoever ratcheted it.
  • Nothing checks that a test asserts the intended behaviour rather than the observed behaviour. OPAUDIT 022 states that the comparator must be mutation-tested before it is trusted, and that the agent who writes a check must not be the agent whose work it checks. Neither constraint was in force here, and a test written to assert a fault survived eighteen days and three agents.
  • A repair to one skin does not ask which other skins share the fault. This cost eighteen days on PARADE and could have cost HEURISTIC too had HEURISTIC's ring been live. When a commit is found to have removed something from a shared pattern, the repair must enumerate every skin that commit touched. No process step requires this.
  • WITHDRAWN — this audit's own error, corrected 16 October. The first version of this section claimed pa_frame_border_px and pa_frame_border_color were read by no PHP and that PARADE's whole IMAGE FRAME section did nothing. That is false. Both are read in core/public-controller.php as the per-grid fallback, through a key assembled at run time as $prefix . '_frame_border_px', so the literal string never appears in the file and a search for it finds nothing. The controls work. The mistake was searching for a name the source never spells out — the same error made twice more the same day, once on parade_wave_row and once here. Recorded rather than deleted, because a search proving absence is only as good as the name being searched for, and that is worth knowing.
  • Two tests fail for an environmental reason and should be made to say so. desktop-auth-route-regression and pixelix-compat-regression both read a .htaccess that is untracked and therefore absent in any worktree. They fail identically with no changes applied. A test that cannot distinguish a missing fixture from a real fault trains agents to discount failures.
  • Which other grid skins carry a dormant ring is not established. HEURISTIC's was checked and is correctly dormant. The same "deferred, no engine" note may sit above live or dead CSS in skins not examined here. The note cannot be trusted on its own; only the manifest's required engines and control sections settle it.

9. What this audit does not claim

It does not claim the feature works on the owner's site. It works in a harness, measured, and the skin has not been packaged. It does not claim AURORA and JIVE TURKEY are correct in general; it claims their rings were measured painting and animating in a harness today, and that no live site in the fleet that could be reached runs either skin, so neither was verified live. It gives no undertaking that agents will check adjacent skins in future, because that undertaking is what section 8 asks to be replaced with a check.

1. Summary

Every like from a Pixelfed follower resolved to nothing and was dropped, each one showing in the inbox log as unresolved. The cause was a mismatch in how Pixelfed names the thing being liked versus how our resolver looked it up.

2. What a human saw

Likes from Pixelfed followers didn’t register on the liked post, and the inbox log marked every one of them UNRESOLVED.

3. Root cause

A Like from Pixelfed points at the Note’s human permalink (for example /ig-20260624-061822-0705), not the machine address (/ap/note/p/N) that our resolver knew how to match. So the resolver was handed an address it didn’t recognise, matched nothing, and the like was dropped on the floor.

4. Evidence at diagnosis

The inbox log — built precisely to catch drops — showed every Pixelfed like arriving and resolving to nothing. The address in each one was the public permalink, not the machine id, which named the exact mismatch.

5. What we did

The resolver now also accepts the public permalink form: it looks the slug up and maps it to the post when the image belongs to one (matching how the machine id resolves) or to the standalone image otherwise. The database handle was threaded into all four inbox call sites so every path can resolve the same way.

6. Verified live — and what remains

The fix is in and matches how the machine-id path already resolves, but a live like from a Pixelfed follower landing on the right post has not yet been named as watched. Until then this stays Fixed — confirming.

7. Eyeball next

Watch one real Pixelfed like resolve and register on the correct post in the inbox log.

8. The doctrine this incident reinforced

The log we built to catch drops caught this one — the payoff of instrumenting first (OPAUDIT 005). And the specific lesson: a peer may refer to your content by a different address than you handed it, so a resolver has to accept every address a real peer will actually use, not only the canonical one.

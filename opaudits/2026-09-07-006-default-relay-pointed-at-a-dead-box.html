OPAUDIT 006 — The default network relay pointed at a machine that no longer existed

1. Summary

The built-in default address for the network relay still named a server that had been retired. Any install that hadn’t set its own relay address aimed every join at a dead inbox — and, being a relay join, failed with no error anyone would see.

2. What a human saw

Nothing — which was the problem. Joins to the network relay simply didn’t take, including from the fleet hub, with no visible failure to explain why.

3. Root cause

The default relay address pointed at the old standalone relay box, which had been decommissioned. With no live inbox at that address, every join sent to the default went nowhere, and the join path had no loud failure for a dead-inbox case.

4. Evidence at diagnosis

Installs without an explicit relay address failed to join while ones with a correct explicit address succeeded — isolating the fault to the built-in default rather than the join code.

5. What we did

The default now points at the live network actor (https://photoblogs.fyi/ap/actor), which has a real inbox that turns a follow into a relay join. An explicit per-site relay address still overrides the default for anyone who sets one.

6. Verified live — and what remains

The fleet is on the relay, but that join was achieved through explicit configuration during a fleet-join session, not by relying on the corrected default. What has not been watched yet is a brand-new install joining the relay cleanly on the new default alone. Until that is seen, this stays Fixed — confirming.

7. Eyeball next

Stand up a fresh install with no relay address set and watch it join the live relay on the default — the observation that turns this green.

8. The doctrine this incident created

A default deserves the same proof as a feature. A built-in value that points at something no longer alive doesn’t announce itself — it just quietly does nothing. When a dependency is retired, every default that named it has to be found and re-pointed, and then watched.

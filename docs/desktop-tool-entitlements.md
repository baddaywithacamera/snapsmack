# SnapSmack Desktop Tool Entitlements

**Status:** Required before public distribution  
**Applies to:** SNAP SLAPPER and ACTION LAB

## Product boundary

SNAP SLAPPER and ACTION LAB are free companion products for people who own and run their own SnapSmack CMS installation. They are not separately sold subscriptions. Neither application runs as a free-standing public tool: the user's own CMS installation generates the entitlement API key required to start it.

This boundary is intentional. It keeps the tools, documentation, compatibility promises, and support obligation inside the SnapSmack ecosystem instead of turning them into general-purpose products supported across every possible website and workflow.

## Entitlement rules

- The user's own SnapSmack CMS generates the API key used to unlock each protected desktop tool.
- There is no separate charge for the tools. A valid SnapSmack installation includes their use.
- The key proves that the user has their own installation; it is not a paid licence term.
- A valid key grants **90 days** of use.
- The desktop tool must clearly show the entitlement expiry date.
- After expiry, the tool enters a **14-day grace period** so temporary server, network, or renewal trouble does not immediately interrupt work.
- Grace is continuity time, not free bonus time.
- When renewed during grace, the next 90-day entitlement remains anchored to the previous entitlement's expiry date. Days already consumed in grace are therefore subtracted from the usable time remaining on the renewed key.
- Example: a key expires March 31. The user renews on April 10 after consuming 10 grace days. The renewed entitlement still follows the March 31 renewal boundary; those 10 days do not move the next expiry ten days later.
- After the 14-day grace period ends, protected application features do not run until the CMS issues a valid renewal key.
- A new entitlement after a genuine lapse begins from the CMS-authorized issuance boundary; the user's CMS is authoritative about whether a reissued key continues an existing term or begins a new one.

## Required user experience

- First launch explains that the application is included free with the user's own SnapSmack installation and requires a key generated by that CMS.
- The key-entry screen identifies where in the CMS to generate or renew it.
- Valid, expiring soon, grace, and expired states are visually distinct and written in plain language.
- The application warns before expiry and again when grace begins.
- An expired entitlement never deletes photographs, presets, metadata, albums, or organizer data.
- Users can still retrieve their locally generated/exported files after expiry; the lock applies to running protected tool features, not ownership of user output.
- Error messages distinguish an invalid key, expired key, unreachable CMS, clock problem, and unsupported CMS version.

## Enforcement design

- The user's own CMS installation is the entitlement authority.
- Keys must be signed or server-validated so changing a local JSON file cannot extend a term.
- The desktop application stores only the minimum entitlement state needed for offline continuity.
- Local state records the last successful validation time and entitlement boundary to detect simple clock rollback.
- Validation failures must not expose CMS credentials or entitlement signing secrets.
- The CMS signing secret never ships inside either desktop executable.
- Revocation and device limits, if any, must be explicit policy decisions rather than accidental side effects of implementation.

## Support boundary

- Supported environment: current supported SnapSmack CMS plus the published Windows/Linux application builds.
- No promise of compatibility with unrelated CMS products.
- ACTION LAB may emit Lightroom-compatible presets, but ACTION LAB itself remains a SnapSmack-only tool.
- Lightroom compatibility describes the generated preset format; it does not turn ACTION LAB into an independently supported Lightroom product.

## Decisions still required

- One key per tool, one shared desktop-tools key, or entitlements carried in one signed token.
- Whether keys bind to a CMS installation, user, device, or a limited device set.
- The CMS endpoint and signed payload format.
- Validation frequency while a key remains valid.
- Revocation behavior for compromised keys.
- Exact read-only behavior after expiry, if any, beyond access to already exported user files.
